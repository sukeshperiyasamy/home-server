# Backup Philosophy & Strategy

## Core Principles

1. **Storage Is Not Backup**: Storing data on `/mnt/storage` provides persistence, not redundancy. A single physical drive failure can destroy all data.
2. **GitHub Is Not a Personal Data Backup**: GitHub stores only configuration, scripts, and documentation. No personal media, documents, or database secrets are ever stored in Git.
3. **Application-Aware Backups**: Live databases (such as SQLite in WAL mode) cannot be safely backed up by simple file copies while active; application-aware dumps using SQLite's Online Backup API are required.

> [!WARNING]
> **Single Drive Failure Risk**: Currently, `/mnt/storage/backups` resides on the **same physical hard drive** (`/dev/sda7`) as the live application data (`/mnt/storage/app-data`). This protects against accidental file deletion, database corruption, or bad container updates, but **DOES NOT protect against physical drive failure, motor burnout, or hardware loss**. True redundancy requires implementing the off-site / second-drive tiers outlined in the 3-2-1 strategy below.

---

## 3-2-1 Strategy (Roadmap)

For true resilience, the server is designed around the 3-2-1 backup framework:
* **3 Copies of Data**: Primary data, local snapshot archive, off-site encrypted backup.
* **2 Different Media**: Primary USB HDD and secondary storage (e.g. secondary external disk or network share).
* **1 Off-Site Copy**: Encrypted cloud storage (e.g. Backblaze B2 / Rclone) or remote secondary server synchronized privately over Tailscale.

## Vaultwarden Backup Implementation (Phase 7)

### What Is Backed Up
* **`db.sqlite3` Snapshot**: Generated using SQLite's native Online Backup API (`sqlite3 .backup`). This checkpoints the WAL (Write-Ahead Log) into a single, ACID-compliant, non-torn database snapshot.
* **`rsa_key.pem`**: The server RSA private key used to sign JWT authentication tokens and session ciphers.
* **`rsa_key.pub.pem`**: Server public key (if present).
* **`attachments/`**: User-uploaded vault cipher file attachments.
* **`sends/`**: Bitwarden Send encrypted attachments.
* **`metadata.json`**: Autogenerated backup metadata containing ISO-8601 UTC timestamp, Vaultwarden container image version, SQLite integrity check status (`PRAGMA integrity_check`), and backed-up file manifest.

### What Is Intentionally Excluded
* **`db.sqlite3-wal` & `db.sqlite3-shm`**: Not needed because the SQLite Online Backup API automatically incorporates unflushed transactions into the standalone backup database. Copying raw WAL/SHM files live can cause database corruption.
* **`icon_cache/`**: Cached website favicons, which are non-critical and re-downloaded automatically on demand.
* **`tmp/`**: Ephemeral in-flight chunked upload fragments.

## Operational Procedures

### 1. Running a Manual Backup
Execute the backup script on the Raspberry Pi:
```bash
/home/sukesh/home-server/scripts/backup.sh
```
* **Exit code `0`**: Backup created and verified successfully.
* **Exit code `1` or `2`**: Prerequisites missing or database integrity check failed (aborts without corrupting existing backups).

You can override the retention period (default: 30 days) via environment variable:
```bash
RETENTION_DAYS=60 /home/sukesh/home-server/scripts/backup.sh
```

### 2. Listing Existing Backups
```bash
ls -lh /mnt/storage/backups/vaultwarden/
```
Backups are organized by timestamp:
```text
/mnt/storage/backups/vaultwarden/
├── vaultwarden_backup_YYYYMMDD_HHMMSS.tar.gz
├── vaultwarden_backup_YYYYMMDD_HHMMSS.tar.gz.sha256
├── latest.tar.gz -> vaultwarden_backup_YYYYMMDD_HHMMSS.tar.gz
└── latest.tar.gz.sha256 -> vaultwarden_backup_YYYYMMDD_HHMMSS.tar.gz.sha256
```

### 3. Verifying a Backup Archive
To verify that an archive is intact without modifying any system state:
```bash
cd /mnt/storage/backups/vaultwarden

# Verify SHA256 cryptographic checksum
sha256sum -c vaultwarden_backup_YYYYMMDD_HHMMSS.tar.gz.sha256

# Inspect archive contents
tar -tvf vaultwarden_backup_YYYYMMDD_HHMMSS.tar.gz

# Verify SQLite database integrity from the archive
tar -xzf vaultwarden_backup_YYYYMMDD_HHMMSS.tar.gz -O vaultwarden_backup/db.sqlite3 > /tmp/check.sqlite3 \
  && sqlite3 /tmp/check.sqlite3 "PRAGMA integrity_check;" \
  && rm -f /tmp/check.sqlite3
```

## Restore & Disaster Recovery Procedures

### Standard Restore (Existing Machine)
To restore Vaultwarden to a previous backup snapshot:
```bash
/home/sukesh/home-server/scripts/restore.sh /mnt/storage/backups/vaultwarden/vaultwarden_backup_YYYYMMDD_HHMMSS.tar.gz
```
Or restore from the latest snapshot:
```bash
/home/sukesh/home-server/scripts/restore.sh /mnt/storage/backups/vaultwarden/latest.tar.gz
```

**What the restore script does automatically**:
1. Verifies the SHA256 checksum of the target archive.
2. Inspects and extracts archive contents into a temporary staging area.
3. Runs `PRAGMA integrity_check;` on the extracted database.
4. Stops the running Vaultwarden container (`docker compose stop vaultwarden`).
5. Creates a **pre-restore safety snapshot** of the live data at `/mnt/storage/app-data/vaultwarden.pre-restore-<timestamp>`.
6. Deploys the restored database, RSA keys, and attachment files.
7. Restarts Vaultwarden and waits for the container health check to report `healthy`.
8. Verifies the API endpoint responds with `HTTP 200`.

### Disaster Recovery (Fresh Raspberry Pi)
If the Raspberry Pi SD card or OS fails completely, disaster recovery follows this sequence:

1. **Flash OS**: Flash a new SD card with 64-bit Debian / Raspberry Pi OS.
2. **Mount Persistent HDD**:
   Connect the USB HDD, locate partition UUID (`blkid`), and add mount entry to `/etc/fstab`:
   ```text
   UUID=3EE45445E4540217  /mnt/storage  ntfs3  nofail,x-systemd.device-timeout=15s,uid=1000,gid=1000,dmask=0022,fmask=0022,iocharset=utf8  0  0
   ```
   Mount the drive: `sudo mount -a`.
3. **Clone Infrastructure Repository**:
   ```bash
   git clone git@github.com:sukeshperiyasamy/home-server.git /home/sukesh/home-server
   ```
4. **Install Docker Engine & Tailscale**:
   Follow steps documented in `docs/INSTALLATION.md`.
5. **Verify or Restore Data**:
   Because `/mnt/storage/app-data/vaultwarden` lives on the persistent external HDD, the existing database is already intact.
   If restoring to an earlier clean snapshot is required, run:
   ```bash
   /home/sukesh/home-server/scripts/restore.sh /mnt/storage/backups/vaultwarden/latest.tar.gz
   ```
6. **Deploy Containers**:
   ```bash
   cd /home/sukesh/home-server
   docker compose up -d
   ```
7. **Re-enable Tailscale Serve**:
   ```bash
   sudo tailscale serve --bg http://100.96.171.29:8080
   ```

## Technical Notes: SQLite & Filesystem Considerations

* **WAL Mode (Write-Ahead Logging)**: SQLite in WAL mode writes transactions to `-wal` and `-shm` before checkpointing to `db.sqlite3`. Never copy files using `cp` while the database is live.
* **NTFS (`ntfs3`)**: The storage filesystem is NTFS. Linux POSIX permissions and user ownership are simulated at the mount level. Packing backups into standard `.tar.gz` archives encapsulates files cleanly and ensures full cross-platform portability.
